# データモデル

保存先はPostgresです。画面ごとではなく、考え方ごとに1つのテーブルを使います。

## すべての記録画面を支える1つの保存先

`/tracking`、`/health/water`、ダッシュボードの簡単な入力は、**1つの保存先を見る3つの画面**です。別々の保存先ではありません。

| オブジェクト | 内容 |
|---|---|
| `metric_definitions` | 記録項目の定義。単位、1日分の集計方法、妥当な範囲、グラフ、領域、初期目標を持ちます。所有者のない行はシステムの項目、所有者のある行は自分で定義した項目です |
| `metric_entries` | すべての領域の測定値と時系列 |
| `user_metric_settings` | 項目ごとの自分の目標、表示状態、並び順。行がなければ初期値を使います |
| `metric_daily` | 人、記録項目、日ごとに1行を、その項目自身の規則で集計したビュー |

2.x版は同じ数字を複数の場所に書き込み、内容がずれていました。これを直したことが、再構築で最も価値のある変更です。

## ほかを読む前に知っておきたい3つの判断

### 1日分の集計方法は見た目だけの違いではありません

記録項目には、**合計する**もの（水分、歩数、カロリー）と、**最新を使う**もの（体重、血圧、睡眠、気分）があります。

この1つの設定が、1日の値の出し方と、同じ日に2件目を入力したとき新しい測定として扱うか訂正として扱うかの両方を決めます。迂回できるサービスのコードではなく、データベースのインデックスで守ります。

### 日付は自分の端末から決まります \{#the-date-comes-from-your-device}

日々の記録における「今日」は、**本人にとっての今日**です。UTC+5の地域で午前2時に水を記録したなら、それは今日です。サーバーの時計から日付を決めると昨日に分類され、その人の1日が夕方7時にリセットされたように見えます。

時差を知っているのは端末なので、クライアントが日付を指定します。決め打ちの初期値はありません。

### 単位は各入力に残ります

メートル法からヤード・ポンド法に切り替えても、12年分の記録の意味が黙って変わってはいけません。履歴には入力時の単位を残し、読むときに変換します。

## ほかのテーブル

この中心の周りには、領域ごとのテーブルがあります。症状と発生記録、薬と服用、食事と保存した食事、月経周期の日付、子どもとその記録、人と人の関係、思い出とアルバム、メモとフォルダー、予定と確認リスト、チャットとメッセージ、コミュニティ投稿、専門職の掲載情報、献血者の掲載情報、アカウント自身の行などです。

全一覧と、各テーブルの内容・エクスポート方法は[エクスポートファイルの形式](../reference/export-format.md)をご覧ください。エクスポート自体と同じ一覧から作られるため、実際のファイルにないテーブルを説明できません。

## 常設の行と日付のある行

すべてのテーブルはどちらかに分かれ、この違いが製品全体に関わります。

- **日付のある行**は1日に属します。測定、服用、食事、予定などです。
- **常設の行**は、日付のある行の*意味*を支えます。薬、症状、保存した食事、目標などです。

期間で絞るのは前者だけです。後者まで除くと、どの薬を服用したか分からない一覧になり、単に小さなエクスポートではなく壊れたものになります。

## 意図してモデル化していないもの

- **健康の点数、連続記録、順位、レベルはありません。** 日々の記録と健康の記録は観察であり、人の価値を測るものではありません。別の[紹介プログラム](../features/referrals.md)では、確認された招待にポイントやバッジが付く場合がありますが、健康や日々の行動を採点しません。
- **メールアドレスの列はありません。** メールアドレスは認証サービスが管理します。もう1つコピーを作ると2つの書き込み元ができ、最初の変更でずれます。
- **位置情報を共有する範囲はありません。** 共有できるものの列挙値は記録項目、薬、家系図の3つで、位置情報は含まれません。
