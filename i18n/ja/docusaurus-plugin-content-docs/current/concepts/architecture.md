# アーキテクチャ

LifeWellは**静的なシングルページアプリ**です。ビルドによってファイルのフォルダーが作られ、そのフォルダー全体を公開します。構成の中にNodeサーバーはありません。

## 全体像

```text
ブラウザー／AndroidのWebView
        │
        ├──────────────► PostgREST経由のPostgres    （通常の読み取りと書き込み）
        │                 · 行単位のアクセス制御
        │                 · 列ごとの権限
        │                 · 一覧は最大50行
        │
        └──────────────► DenoのEdge Function       （ブラウザーに置けないものだけ）
                          · 不正利用の検査を伴う2つの公開フォーム
                          · 読み取り専用の共有リンクの解決
                          · Google Driveのトークン交換
                          · AI推定と自分のAIキー
                          · 予定を設定したエクスポート
                          · Playでの購入の検証
                          · 管理者によるアカウント操作
```

## 使い分けを決める1つの規則

> 通常のデータについてはブラウザーからデータベースに直接接続します。Edge Functionを使うのは、秘密情報、昇格した権限、利用者が入力したものへの信頼など、**ブラウザーが保持してはいけないもの**を操作が必要とする場合だけです。

そのほかは本人として直接クエリを実行し、[プライバシーとセキュリティ](./privacy-and-security.md)に記載した規則が適用されます。

## 権限の境界をデータベースに置く理由

アプリのコードだけで認可すると、呼び出し場所のすべてで検査を忘れない必要があります。行単位のアクセス制御では*データベース*が制限するため、間違ったクエリでも別の人の行を返す代わりに何も返しません。

同じ理由で、実行中のアプリにORMはありません。スキーマはTypeScriptで記述し、実行前にマイグレーションへ変換しますが、アプリはログインした本人としてクライアントライブラリ経由でだけ接続し、データベースの規則が適用されます。

## 使用する技術

| 層 | 採用したもの |
|---|---|
| フレームワーク | React 19 |
| ビルド | Vite 8。公開版にソースマップは含めません |
| ルーティング | 型付き検索パラメータを持つファイルベースのルート |
| サーバーの状態 | TanStack Query |
| クライアントの状態 | Zustand。アプリの状態にReact Contextは使いません |
| フォーム | React Hook FormとZod。同じZodスキーマでEdge Functionも検証します |
| アクセシビリティ | React Aria ComponentsがDOM、ARIA、キーボード操作を担当します |
| 表示 | Tailwind v4。設定ファイルではなくCSSで設定します |
| グラフ | D3 |
| リッチテキスト | Tiptap。製品に標準のテキストエリアはありません |
| 端末内の保存 | ブラウザーの保存先に触れることを許された1つのライブラリ |
| Android | Capacitor 8 |

## Firebaseを使わない理由

2.x版はFirebaseで動いていました。無料枠の1日の読み取り上限に達すると、リセットされるまで実際の利用者全員が丸1日使えなくなるという問題が、再構築の理由の1つです。

もう1つは共有の仕組みです。記録の一部を名前を指定した相手に見せるには、行ごとの判断が必要です。Postgresはデータベース内で判断できます。以前のドキュメント型の保存先では、すべてのクエリと歩調を合わせる規則ファイルで判断していました。

## URLに保存する状態

モーダル、タブ、絞り込み、並べ替え、ページ位置、検索語は、部品の一時的な状態ではなくアドレスバーに保存します。更新しても見ていた場所が失われず、表示中の内容へのリンクをそのまま共有できます。
