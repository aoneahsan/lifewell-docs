# 数据模型

使用 Postgres。每个概念一张表，而不是每个页面一张表。

## 所有记录工具共用一份存储

`/tracking`、`/health/water` 和首页快捷操作是**同一份存储的三个视图**，不是三份存储。

| 对象 | 作用 |
|---|---|
| `metric_definitions` | 记录工具定义目录——单位、一天如何汇总、合理范围、图表、所属领域和默认目标。没有所有者的行是系统提供的工具；有所有者的行是您自定义的工具 |
| `metric_entries` | 所有领域中的每次读数，组成时间序列 |
| `user_metric_settings` | 您为每种记录工具设定的目标、可见性和顺序。没有对应行时，采用默认设置 |
| `metric_daily` | 一个视图：按人、记录工具和日期各汇总一行，并遵守该工具自己的规则 |

2.x 应用曾将同一个数字写入多个地方，内容逐渐不同步。修复这一点，是重建中价值最高的一项改变。

## 阅读其他内容前值得知道的三项决定

### 一天如何汇总，不只是显示问题

记录工具要么**累加**（饮水、步数、热量），要么**以最新记录为准**（体重、血压、睡眠、心情）。

同一个字段既决定一天如何计算，也决定同一天的第二条记录是新读数还是修正。规则由数据库索引执行，而非交给可能被绕过的服务。

### 日期来自您的设备 \{#the-date-comes-from-your-device}

每日记录工具中的“今天”，是**记录者所在地点的今天**。UTC+5 地区的人凌晨两点记下一杯水，记的仍是当天；若按服务器时钟算日期，记录可能落到昨天，页面看起来会在傍晚七点重置。

只有设备知道当地时差，因此由客户端指明是哪一天。这里没有可以随意套用的默认值。

### 每条记录都保存单位

从公制改为英制时，不能悄悄重新解释十二年的历史记录。每条记录都保留写入时使用的单位，显示时才进行换算。

## 其他部分

围绕这个核心，各领域分别有表：健康状况及发作、药物及服药、餐食和收藏餐食、周期日期、孩子及其记录、人物及其关系、回忆和相册、笔记和文件夹、日历事件和清单、聊天与消息、社区帖子、专业人员名录、献血者名录，以及账号自身的记录。

完整清单、每张表的内容和导出方式见[导出文件格式](../reference/export-format.md)。该页面与导出功能读取同一份注册表生成，因此不会描述文件里不存在的表。

## 长期有效的记录与带日期的记录

每张表都属于其中一种，这种区别贯穿整个产品：

- **带日期的记录**属于某一天，例如读数、服药、一餐或预约。
- **长期有效的记录**说明带日期的内容*意味着什么*，例如药物、健康状况、收藏餐食或目标。

日期筛选只作用于前者，不作用于后者。只有服药记录、却没有对应药物的清单，不是更小的导出文件，而是损坏的导出文件。

## 有意不建模的内容

- **没有健康评分、连续打卡、排名或等级。** 日常及健康记录写的是观察结果，不是对您的评价。独立的[邀请奖励计划](../features/referrals.md)可为确认的邀请授予积分和徽章；这些奖励不会给健康或日常活动打分。
- **没有邮箱地址字段。** 身份服务商负责您的邮箱；若另存一份，就会有两个写入来源，第一次更改邮箱后便可能过时。
- **没有位置分享权限范围。** 规定可分享内容的枚举只有三类——记录图表、用药信息和关系树——不含位置。
